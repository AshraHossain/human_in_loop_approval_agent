# Human-in-the-Loop Approval Agent

A LangGraph agent that gates Jira writes behind a **durable** human approval
step — one that survives the process exiting.

When a request clears policy, it runs. When it doesn't, the agent calls
`interrupt()`, persists its entire state to a SQLite checkpointer, and **exits**.
A later `approve` command resumes the graph from that checkpoint in a brand new
process. The pending approval is a row on disk, not a thread parked in memory,
so it survives a crash, a reboot, or an approver who is asleep.

```
submit → assess ─┬─(auto)─────────────────→ execute → END
                 └─(gate)→ approval_gate ──┬─(approve)→ execute → END
                            [interrupt()]  └─(deny)────→ denied  → END
```

## The invariant

> Confidence may only ever **escalate** to a gate.
> It can never clear one that policy requires.

Risk tier is derived from the *action* (`transition → Done` is high, always),
never from how confidently the request was worded. A high-confidence score on a
high-tier action still pauses. That one rule is the difference between
human-in-the-loop and human-in-the-loop theater, and it is asserted directly by
`tests/test_policy.py::test_high_confidence_cannot_clear_a_policy_gate`.

## Running it

```bash
uv sync
uv run pytest -q                        # test suite
uv run python -m hitl.cli --help        # CLI
```

A full approval cycle spans **three separate process invocations** — that's the
point:

```bash
uv run python -m hitl.cli submit "transition P-1 to Done" --seed "P-1=To Do"
#   → APPROVAL REQUIRED, prints a request_id, exits

uv run python -m hitl.cli approve <request_id> --as ash --seed "P-1=To Do"
#   → resumes from the on-disk checkpoint, executes, prints: stage: completed

uv run python -m hitl.cli audit <request_id>
#   → replays every stage of the trail, all sharing one request_id
```

## Current status

Jira is **not yet bound**. `getAccessibleAtlassianResources()` returns `[]` —
no Atlassian site is reachable from the connector, so there is no `cloudId` to
call any Jira tool with. Fix by provisioning a Jira Cloud site or re-authorizing
the Atlassian connector with site scope.

Everything is built against the `JiraPort` protocol with an in-memory
`FakeJira`, so the whole graph is complete and tested without a network. Binding
the live API is one class — see Task 7 of the plan.

## Known limitation

`approve --as <human_id>` is **self-asserted identity**. There is no
authentication. Honest for a local single-operator tool; a real hole for
anything carrying compliance weight. Upgrade path: OS user + signed approval
token.

## `archive/` — the retired variants

This started as three implementations of the same pattern —
`agent_executor_version/`, `langgraph_version/`, `runnable_pipeline_version/` —
to compare architectures. Two are retired to `archive/`, working, and the third
became `src/hitl/`.

The comparison stopped being meaningful: **`AgentExecutor` left
`langchain.agents` in langchain 1.0**, and on langchain 1.x `create_agent` is
LangGraph underneath. The AgentExecutor-vs-LangGraph contrast no longer exists
in current LangChain. `archive/agent_executor_version` depends on
`langchain-classic` to keep running at all. Read them as history.

Both archived variants still pass their offline self-checks:

```bash
uv run --project archive/agent_executor_version \
  python -m archive.agent_executor_version.main --self-check
uv run --project archive/runnable_pipeline_version \
  python -m archive.runnable_pipeline_version.pipeline --self-check
```

(The module path includes `archive.` because these use package-relative
imports and the working directory is the project root.)
